# Hybrid-режим CatQuest

Этот документ описывает, как обычный клиент WoW работает с серверной
озвучкой без Lasthavens Addon Manager, почему это не может быть обычным
«прокси файлов» и какие части ещё нужно довести до production-уровня.

## Цель

Hybrid объединяет три источника:

1. локальный voice-pack — готовые дорожки, которые играются сразу и не требуют
   сети;
2. локальный кэш `CatQuest335_ServerVoices` — файлы, скачанные консольной
   утилитой из Voice API;
3. live-companion — внешний процесс, который получает текст от аддона и сам
   запрашивает и проигрывает OGG.

Приоритет источников такой:

```text
локальный voice-pack
        ↓ если дорожки нет
локальный CatQuest335_ServerVoices
        ↓ если файла нет и запущен companion
CatQuestCompanion → Voice API → внешний проигрыватель
```

Без companion отсутствие дорожки считается обычной недоступностью: аддон не
должен бесконечно пытаться читать несуществующий файл и создавать видимость
воспроизведения.

## Компоненты

### Аддон CatQuest

Аддон находится в `Interface\AddOns\CatQuest`. Он умеет:

- выбрать локальную дорожку из установленного voice-pack;
- сформировать путь к серверной дорожке;
- прочитать локальный `CatQuest335_Bridge\Bridge.lua`-манифест;
- передать текст companion-мосту, если серверная дорожка ещё не скачана;
- показать talking-head и субтитры, поставить реплику в очередь и обработать
  `/cq stop` или `/cq next`.

Lua-код не делает HTTP-запросов и не читает файлы с диска. Это ограничение
обычного WoW, а не ограничение самого CatQuest.

### CatQuest Client

Утилита находится в `client/catquest_client.py` и запускается через
`CatQuest-Client.cmd`. В ней есть четыре сценария:

- `sync` — обновить аддон, индекс и готовые OGG;
- `request` — дождаться одной дорожки по ID квеста и сохранить её;
- `watch` — периодически синхронизировать кэш и читать сохранённые записи о
  пропущенных квестах;
- `companion` — читать экранный пиксельный мост и проигрывать live-запросы.

`sync`, `request` и `watch` используют только Python 3.10+ и стандартную
библиотеку. Для `companion` нужны `mss` и `pygame` из
`client/requirements.txt`.

### Локальный серверный аддон

Утилита создаёт:

```text
Interface\AddOns\CatQuest335_ServerVoices\
├── CatQuest335_ServerVoices.toc
├── Bridge.lua
└── <locale>\Sounds\q\<quest>.ogg
```

`Bridge.lua` — не сетевой мост. Это сгенерированный манифест, в котором
перечислены уже скачанные дорожки, их размеры и длительности. После изменения
файлов WoW должен загрузить аддон заново через `/reload`.

### CatQuestCompanion

Это отдельный аддон в `Interface\AddOns\CatQuestCompanion`. Он не вмешивается
в `PlaySoundFile`. Когда CatQuest выбирает live-режим, companion на короткое
время рисует в левом верхнем углу экрана сетку `96 × 8` клеток размером по
4 физических пикселя.

Пиксельный протокол содержит:

- синхронизирующий шаблон;
- номер сообщения, номер части и число частей;
- длину части и checksum;
- UTF-8 payload с типом `Q` для квеста, `G` для gossip и `X` для остановки.

Консольная утилита снимает эту область через `mss`, проверяет checksum,
собирает части, вызывает Voice API и проигрывает полученный OGG через
`pygame`. Поэтому внешний процесс получает не факт вызова `PlaySoundFile`, а
сам текст и метаданные реплики ещё до попытки локального воспроизведения.

## Поток `sync`

```text
CatQuest Client
    │
    ├─ GET /api/v1/release
    ├─ скачать и проверить ZIP CatQuest
    ├─ GET /api/v1/index
    ├─ скачать готовые /api/v1/voice/<id>/<type>
    ├─ записать OGG атомарно
    └─ сгенерировать Bridge.lua
             │
             └─ /reload в WoW
                    │
                    └─ CatQuest видит локальную дорожку
```

Для каждого файла проверяются URL, размер и, если сервер его предоставляет,
SHA-256. ZIP не может записать файл за пределами папки аддона. SavedVariables
WoW утилита не заменяет.

## Поток live-companion

```text
QUEST_DETAIL / QUEST_COMPLETE / gossip
        │
        ▼
CatQuest собирает text + quest ID + locale + NPC metadata
        │
        ▼
CatQuestCompanion рисует несколько pixel-кадров
        │
        ▼
mss → checksum → сборка payload
        │
        ├─ Q → /api/v1/voice/<id>/<DETAIL|COMPLETE>
        └─ G → /api/v1/gossip
                    │
                    ▼
             ожидание генерации
                    │
                    ▼
             cache OGG → pygame
```

Для уже готовой дорожки запрос заканчивается одним скачиванием. Для новой
квестовой дорожки клиент получает `202`, опрашивает `/api/v1/status/...`, а
затем скачивает готовый OGG. Для gossip повторяется запрос с тем же текстом,
пока сервер не вернёт аудио или окончательный статус.

## Почему это сложно

### 1. Нет события на `PlaySoundFile`

Обычный WoW не сообщает внешнему процессу, какой путь аддон передал в
`PlaySoundFile`. Также Lua-аддон не может самостоятельно открыть HTTP или
записать файл в addon-папку. Поэтому внешняя утилита не может быть
прозрачным reverse-proxy, как браузерный менеджер.

### 2. Pixel bridge зависит от изображения

Мост работает поверх скриншота, поэтому на него влияют:

- оконный режим и положение окна WoW;
- масштабирование Windows/DPI и несколько мониторов;
- изменение UI scale;
- оверлеи, захват экрана, цветокоррекция и HDR;
- закрытое или свернутое окно игры;
- потеря одного или нескольких кадров.

Сейчас координаты задаются вручную через `--x` и `--y`, а размер клетки
обычно равен 4 пикселям. Checksum и повтор циклов защищают от большей части
ошибок, но не делают канал таким же надёжным, как named pipe или локальный
IPC.

### 3. Нет обратного подтверждения готовности

Аддон знает, что текст отправлен в companion, но не знает, когда сервер
закончил генерацию и когда `pygame` начал проигрывание. Поэтому talking-head,
субтитры и очередь используют оценочную длительность. При медленной генерации
голова может появиться раньше звука, а при ошибке API аддон узнает о проблеме
только из сообщения консольной утилиты.

### 4. Внешний звук не является звуком WoW

`pygame` играет через системное аудиоустройство, а не через канал SFX WoW.
Настройки громкости WoW, внутриигровое приглушение и часть логики
`PlaySoundFile` на него не распространяются. Остановить внешний звук можно
сообщением `X`, но при аварийном завершении процесса аддон не получит
подтверждение.

### 5. Жизненный цикл файлов WoW

WoW видит addon-файлы через собственный список файлов и загрузку аддонов.
После скачивания новой дорожки нужен `/reload`; простая запись OGG на диск не
гарантирует, что текущая игровая сессия начнёт её читать. Обновление во время
игры также может столкнуться с занятым файлом или с тем, что старая версия
манифеста уже загружена.

### 6. Backend может отвечать не сразу

Генерация зависит от очереди, доступного бюджета, исходного текста и лимитов.
Нужно различать `queued`, `running`, `ready`, `failed`, `limited` и `missing`,
а также не превращать временный сетевой сбой в повреждённый кэш.

### 7. AiQuestVoice — другой транспорт

Старый `AiQuestVoice\bridge.py` использует clipboard, ручной Ctrl+C,
OpenRouter и `pygame`. Это полезный рабочий прототип внешнего проигрывателя,
но он не связан с текущим CatQuest API и не должен запускаться одновременно с
`CatQuest Client companion`: оба процесса могут проиграть одну реплику.

## Что уже сделано

- консольная команда `companion` и пакетирование через `CatQuest-Client.cmd`;
- установка отдельного `CatQuestCompanion` без изменения реальной папки
  `AiQuestVoice`;
- двусторонне согласованный pixel-протокол с chunking, checksum и UTF-8;
- маршруты `Q`, `G`, `X`;
- кэш внешних OGG в `CatQuest335_ServerVoices\companion-cache`;
- опрос статуса квестовой дорожки и повтор запроса gossip;
- защита ZIP-путей, атомарная запись и базовые проверки API-ответов;
- приоритет локального voice-pack и локального server cache перед companion;
- документация запуска и предупреждение о необходимости `/reload`.

## Что доработать

### P0 — необходимо для надёжного первого релиза

1. Провести end-to-end тест на целевой версии WoW: реальный квест, gossip,
   `/cq stop`, `/cq next`, смена языка, оконный режим и два монитора.
2. Добавить автоматическое определение окна WoW и калибровку области захвата,
   оставив `--x`, `--y`, `--cell` как ручной fallback.
3. Добавить обратный канал состояния: хотя бы `received`, `requesting`,
   `playing`, `failed`. Без него UI аддона работает по оценке.
4. Сделать единый lock/instance для companion, чтобы второй процесс не
   проигрывал реплики параллельно с первым или с AiQuestVoice.
5. Обработать аварийное завершение, потерю аудиоустройства и переподключение
   без потери текущего сообщения.

### P1 — качество эксплуатации

1. Добавить retry с exponential backoff, ограничение частоты и понятные
   сообщения для offline, `429`, `5xx` и `limited`.
2. Хранить метаданные кэша: API, locale, client version, hash текста,
   размер, время скачивания и статус. Удалять неполные и слишком старые файлы.
3. Поддержать prefetch: отправлять новые тексты в companion заранее, пока
   игрок читает окно квеста.
4. Добавить отдельные настройки громкости, аудиоустройства и поведения при
   сворачивании WoW.
5. Сделать обновление аддона rollback-safe: staging, резерв предыдущей версии,
   проверка TOC и восстановление после прерванной записи.
6. Добавить режим диагностики: тестовый pixel frame, скрин области захвата,
   latency API, последний decoded payload без сохранения полного текста в лог.

### P2 — архитектурные улучшения

1. Если появится разрешённый локальный helper, заменить pixel bridge на named
   pipe или localhost IPC, оставив pixel bridge как fallback для чистого WoW.
2. Добавить серверный endpoint для custom quest text, чтобы новая реплика могла
   озвучиваться даже без заранее загруженного quest catalog.
3. Согласовать с backend единый протокол job ID для квестов и gossip вместо
   повторной передачи полного текста gossip при каждом poll.
4. Добавить автоматические тесты Lua-протокола: одинаковый payload должен
   одинаково кодироваться в Lua и декодироваться Python.
5. Собрать подписанный standalone `.exe`, чтобы обычному игроку не требовалась
   установка Python и зависимостей.

## Минимальная проверка перед выпуском

```powershell
python -B client/catquest_client.py --version
python -m py_compile client/catquest_client.py
node --check lasthavens-addon-manager/runtime-core.js
git diff --check
```

После этого нужна ручная проверка в игре:

1. установить `CatQuest` и запустить `CatQuest-Client.cmd companion`;
2. выполнить `/reload`;
3. открыть квест, которого нет в локальном кэше;
4. убедиться, что консоль получила `Q`, сервер вернул OGG, а звук запустился
   один раз;
5. нажать `/cq stop` и проверить остановку внешнего звука;
6. проверить локальный voice-pack и готовый server cache — они не должны
   уходить в companion.

## Критерий готовности

Hybrid можно считать готовым для обычных клиентов, когда локальные дорожки и
live-дорожки выбираются предсказуемо, companion автоматически восстанавливает
связь после ошибок, UI получает хотя бы приблизительное состояние внешнего
проигрывания, а установка не требует ручного редактирования Lua, координат
экрана или запуска двух конкурирующих мостов.
