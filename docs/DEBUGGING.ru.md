# Отладка озвучки

В аддоне 0.10.96 и расширении 0.6.62 появились связанные отчёты. Для клиентских событий нужны обе новые версии и полная перезагрузка страницы игры после обновления.

В 0.10.93 / 0.6.59 исправлено измерение длительности: новый шрифт и мост объявляют `readyMetrics=2`. Для этой калибровки также нужны обе новые версии.

В 0.10.96 / 0.6.62 расширение больше не делает фоновые status-проверки, синхронные
сетевые чтения и readiness-поллинг. Ошибка on-demand дорожки не запускает новый
запрос от обычного игрового read: повтор возможен только новым кликом «Прослушать».
Автоповторы сохранены отдельной настройкой CatQuest и по умолчанию выключены.
Логи и счётчики пишутся пакетно, чтобы не забивать вкладку chrome.storage-операциями.
Окно «озвучка по запросу» также скрыто по умолчанию: включите в настройках CatQuest
пункт «Показывать окно запросов озвучки (для отладки)», если нужно видеть очередь,
статусы и лимиты сервера.

## Как прислать отчёт

1. Повторить проблему с одним квестом или диалогом.
2. В настройках CatQuest нажать **Отладка**, либо ввести `/cq debug`.
3. Нажать **Обновить**, затем **Выделить всё (Ctrl+C)**, нажать Ctrl+C и прислать текст.
4. В настройках расширения открыть диагностику и скопировать её журнал. Прислать оба текста вместе.

Окно игрового отчёта не обновляется постоянно: это снимок по кнопке. Оно содержит настройки звука, возможности моста, активную дорожку, до 30 элементов каждой очереди и последние 300 событий. В событиях сохранены версия, сессия страницы, время, ключ/ID/тип дорожки, слот предзагрузки, канал, длительность, попытка проверки, запрошенный/фактически загруженный шрифт и результат измерения. Старый `/cq log` остаётся кратким выводом в чат; `/cq log clear` очищает игровой журнал.

В расширении хранятся до 300 событий за сессию браузера; запись в session storage группируется с задержкой 1 с. Счётчики telemetry также сбрасываются одной пакетной записью раз в 2 с.

## Как читать этапы

`bridge.contactPage` игрового отчёта соответствует `run` расширения. Затем сопоставляются `slot`, ID и тип квеста (`DETAIL` / `COMPLETE`); для диалогов и повествований также используется путь/слот диалога/хеш книги. `request` связывает отправку через мост с обработкой запроса в background. Слоты переиспользуются после 512 запросов; для очень длинной сессии важны также время и тип/ID.

| Событие | Что известно |
| --- | --- |
| `queued` | Аддон поставил элемент в очередь. До выделения слота виден в игровом отчёте. |
| `packet`, `prefetch-received` | Аддон отправил команду; расширение декодировало её. |
| `bridge-send`, `backend-request` | Запрос передан мосту; background начал HTTP-запрос. |
| `backend-headers` | Получены HTTP-статус и Content-Type; тело ещё может загружаться. |
| `backend-body`, `fetch-done` | Тело загружено либо получен ответ без аудио/ошибка. Видны байты и время. |
| `missing-text` | Сервер подтвердил принятую заявку, но текста стадии пока нет; сетевые повторы для неё отключены до обновления каталога. |
| `prefetch-retry` | Назначена следующая асинхронная попытка; при 429 задержка берётся из `Retry-After`, минимум 5 секунд. |
| `shared-ready`, `prefetch ready` | Байты опубликованы для игрового воркера. |
| `signal`, `font-fs` | Расширение увидело чтение сигнального файла и вернуло шрифт либо отсутствие файла. |
| `client-stage font-probe` | Lua действительно вызвал проверку готовности; номер попытки 1–16. |
| `client-stage font-missing`, `font-ready` | Lua не получил ожидаемый шрифт либо подтвердил его и декодировал длительность. |
| `play-call`, `playing` | Вызван API воспроизведения / API вернулся без обнаруженной ошибки. |
| `audio-delivered` | Виртуальная файловая система вернула байты аудио. |
| `finished` | Истёк таймер длительности аддона. |
| `stopped`, `skipped`, `timeout`, `error` | Пользователь остановил/пропустил дорожку либо аддон обнаружил таймаут/ошибку. |

Успешный HTTP, ответ VFS и возврат PlayMusic/PlaySoundFile — разные подтверждения. Клиент 3.3.5 не даёт надёжного события «звук действительно слышен»; завершение таймера также не доказывает воспроизведение. Отсутствие события означает «не наблюдалось», а не автоматически ошибку: файл мог быть прочитан из кеша клиента, журнал мог обрезаться, версии могут не поддерживать этот этап.

Клиентские отметки передаются через отдельные локальные тихие файлы по одному на этап и слот. Они не запускают сетевой запрос и не ускоряют проверки готовности. Для повторных проверок предусмотрены 16 отдельных отметок; остальные этапы передаются один раз. Манифест этих файлов общий для воркеров. Подробные пути и измерения остаются в игровом отчёте, не упаковываются в новые длинные сообщения.

HTTP-запрос аудио ограничен 95 секундами (бек ждёт готовность до 90 секунд), статус — 15 секундами, ответ моста — 100 секундами. Это асинхронные таймауты, они не блокируют игровой поток. Старые механизмы чтения файлов клиента этим изменением не заменены.

Если виден `HTTP 429`, сначала смотрите пару `backend-headers` → `backend-body` и
поле `retryAfter`/`Retry-After`. Повторная запись `backend-request` до истечения
этого времени — ошибка клиента или старой версии расширения. Для `missing_text`
повторять запрос не нужно: это отсутствие стадии в каталоге, а не временная
генерация.

## Проверки реализации

`validation/diagnostics.lua` проверяет ограничение журнала, копируемый снимок, расхождение шрифтов, отсутствие фонового обновления окна и подавление повторных клиентских отметок. `validation/diagnostics.mjs` проверяет стадии HTTP 200/429/сетевой ошибки, общие ID, пакетную запись, ограничение истории и экспорт. `validation/shared-prefetch.mjs` проверяет клиентские отметки и выдачу аудио без входящих JS-колбэков игрового воркера.

Тесты Chrome с локальными VFS/FS-стендами проверяют загрузчик, панель и декодирование настоящей дорожки 12009 COMPLETE. Они не заменяют проверку звука внутри реального клиента WoW. Память общего манифеста проверяется отдельно на 32 воркерах.

### Зависание 11960 DETAIL, 15 ноября 2026

Присланная пара отчётов показала HTTP 200 и 287002 байта аудио, затем успешную загрузку сигнального шрифта. Lua оставался в ожидании после измерения букв; вызова PlayMusic не было. Длительность готового OGG — 36.76 секунды. Старый алгоритм измерял отдельные A/B/C/D/M: если последняя буква учитывается по растровым границам, все четыре цифры округляются к нулю. Эта ветка раньше возвращала false без записи причины.

Новый шрифт содержит фиксированные M=1em и N=10em. Измеряются `MM`, `NM` и `AM/BM/CM/DM`; последняя буква M и постоянные отступы везде одинаковы. Цифра вычисляется из разности с MM и диапазона NM−MM, с допуском 0.20 от целого. Нулевой результат, неверная калибровка и ошибки API теперь записываются как `font-invalid`; сохраняются версия метрик и все исходные ширины. Браузерная часть не меняет аудиофайл.

Причина различия метрик согласуется с терминальным путём `GetCharacterWidth` в [исходниках whoa](https://github.com/whoahq/whoa/blob/master/src/gx/Font.cpp): последняя буква может учитываться по bearing и ширине bitmap. Метод измерения с общим завершающим символом также описан автором [Forever Bridge](https://github.com/0xInuarashi/wow-forever-codex#3-the-companion-encodes-reply-bytes-as-font-widths); тот проект проверял другой клиент и сам по себе не подтверждает поведение нашего WoW 3.3.5.

`node validation/font-metrics.mjs` передаёт шрифты, сгенерированные настоящим runtime, в Lua 5.1 и FreeType. Он воспроизводит нулевую длительность старого алгоритма и проверяет новый на 28 сочетаниях длительности, масштаба и spacing. `node validation/quest-audio-browser.mjs 11960-DETAIL` проверяет точные скачанные байты проблемной дорожки в Chrome: старые одиночные ink-метрики дают 0, новые пары — 36.8 секунды при реальном декодировании аудио 36.76 секунды. Проверены VFS/open/stat-стенды; реальное игровое воспроизведение после обновления ещё требует подтверждения.
